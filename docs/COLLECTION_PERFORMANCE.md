# 수집·조회 성능 검증

2026-10-16 운영 데이터의 복사본과 동일한 입력을 사용해 검증했다. 운영 원본은 비교 실험에서 수정하지 않았다. 아래 시간은 해당 환경의 측정값이며, 제공기관의 실제 API 응답 속도를 보장하는 수치는 아니다.

## 병목과 변경

기존 웹 수동 수집은 작업 한 건마다 약 3 MB의 압축 DB 전체를 내려받고, 원본 API 응답을 기다리는 동안 저장소 잠금을 잡은 뒤, DB 전체를 다시 압축해 저장했다. 작업마다 provider를 다시 만들어 같은 공연장의 조회 캐시도 재사용하지 못했다. 검색·진행 상태 조회 역시 변하지 않은 DB 전체를 반복해서 내려받았다.

- 수집 이력은 기록별 반복 SQL 대신 선택된 기록을 한 번에 집계한다. 검색의 지역·출처별 수집 범위 판정도 한 번에 조회한다.
- DB 읽기는 매 요청마다 현재 revision과 필요한 payload를 한 SQL에서 확인한다. revision이 같을 때만 검증된 압축본을 재사용하므로 다른 서버의 갱신을 TTL 만료까지 기다리지 않는다.
- 빈 수집 큐를 확인했을 뿐인 요청은 압축·전체 DB 쓰기를 생략한다. 실제 자료 변경은 기존 트랜잭션으로 저장한다.
- 웹 수동 수집은 최대 8개 작업(출처별 4개)을 예약하고, DB 잠금 밖에서 원본을 조회한 뒤 결과를 묶어 저장한다. 같은 요청의 provider와 공연장 캐시도 재사용한다. 출처별 실제 HTTP 시작 간격 350ms와 작업당 12초 제한, 상세 갱신은 유지한다.
- 화면의 진행 조회는 중복 요청을 공유하고, 사용자 새로고침이나 쓰기 직후 조회는 반드시 해당 동작 이후에 시작한다. 변경 없는 지역 배열을 재사용하여 지도 마커 전체 재생성을 피한다.

## 실제 자료 비교

운영 복사본은 전체 레코드 6,011개(검색 대상 공연 5,615개), 수집 이력 951개, 요청 작업 11,268개였다.

| 비교 항목 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 수집 이력 조회 중앙값 | 55.64 ms | 12.92 ms |
| 수집 이력 조회 SQL | 2,854회 | 1회 |
| 전국 검색 중앙값 | 16.29 ms | 16.46 ms |
| 압축 DB 크기 | 3,019,945 bytes | 3,060,449 bytes |

수집 이력 전체와 정렬·선택·limit 4개 변형, 검색 30가지 필터의 전체 응답이 동일했다(`snapshotAt` 제외). 운영 복사본의 검색은 기존 구현도 첫 미완료 범위에서 검사를 끝내므로 이번 측정에서 속도 차이가 없었다. 전국 수집을 완료한 별도 복사본에서는 검색이 37.04 → 17.76 ms였다.

인덱스 최초 생성까지 포함한 DB 열기는 372.85 → 381.75 ms, gzip 압축은 172.17 → 173.97 ms였다. 추가 인덱스의 압축 공간 비용 약 40 KB도 비교에 포함했다. [측정 원자료](verification/collection-store-performance.json)

## 수집 처리 비교

운영 DB 복사본에서 같은 상세 40건(KOPIS 20건·문화포털 20건)을 처리했다. 각 응답은 동일한 원본 필드를 반환하는 25ms 모의 응답이며, 실제 SQLite 복원·백업·gzip·스냅샷 커밋 경로를 실행했다. 원본 API와 PostgreSQL 네트워크는 호출하지 않았다. 다른 빌드·테스트 작업을 마친 뒤 단독 재측정한 결과다.

| 비교 항목 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 상세 40건 완료 | 38.98초 | 11.52초 |
| 스냅샷 저장 | 40회 | 12회 |
| 상세 응답 처리 | 40건 | 40건 |
| 보존된 전체 레코드 | 6,011개 | 6,011개 |

이 조건에서 처리 속도는 **3.38배**, 전체 DB 쓰기는 **70% 감소**했다. 전체 공연 데이터와 원본 JSON의 SHA-256이 일치했다. 변경 후에도 출처별 요청 시작 간격은 최소 350ms였다. 실제 운영 속도는 제공기관 응답·한도·네트워크·공연장 캐시 적중 여부에 따라 달라진다. [측정 원자료](verification/cloud-collection-performance.json)

재현 시 원본 DB의 읽기 전용 백업 파일을 지정한다. 실험 변경은 메모리 pool과 임시 SQLite에서만 수행한다.

```powershell
node --import tsx scripts/benchmark-cloud-collection.ts data/performance-baseline/production-before.db
```

## 화면 조회 비교

동일한 실제 GET 응답을 고정하고 진행 조회 응답을 400 ms 지연시킨 상태에서 탭 표시 이벤트 10회를 발생시켰다. 운영 수집 POST는 차단했다.

| 비교 항목 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 진행 조회 요청 | 10회 | 1회 |
| 최대 동시 진행 조회 | 10개 | 1개 |
| 지도 마커 DOM 추가·삭제 | 60회 | 0회 |
| 지도 공연 합계 | 5,600개 | 5,600개 |

검색·지도 API의 추가 요청은 두 경우 모두 0회였다. 정상 진행 조회 주기 3초와 대기 시 60초는 유지한다. 인접한 성공 조회와 1초 이내로 겹치는 정기 조회만 생략한다. [변경 전](verification/bootstrap-performance-before.json) · [변경 후](verification/bootstrap-performance-after.json)

상태 조회만 30초 후 실제 요청을 취소하고 재시도할 수 있게 했다. 취소 뒤 늦게 도착한 응답은 적용하지 않는다. 수집·검색·엑셀 요청에는 이 제한을 적용하지 않는다.

## 회귀 검증

전체 자동 테스트 **189/189**와 TypeScript·배포 빌드를 통과했다. 중복 tick·출처별 요청 간격·한도와 인증 오류·3회 실패·취소 뒤 늦은 응답·중단/재개·임대 만료 뒤 재선점·저장 실패 뒤 복구·자동 갱신과 상세 버전 충돌·원본과 좌표 및 메모 보존을 포함한다. 전국·지역 검색 판정, 지도·3D·엑셀의 기존 테스트도 통과했다.

## 운영 배포 확인

운영 주소는 https://culture-desk.vercel.app 이다. `65e11f6`의 배포에서 기존 대기 작업을 이어가는 tick을 1회 실행했다. 새 수집 범위는 만들지 않았다.

- 실제 API 작업 20개를 3개 묶음으로 9.146초에 처리했다. 완료 작업 수는 8,175 → 8,195였다.
- 해당 요청이 진행 중일 때 검색을 시작해 HTTP 200, 583ms 응답을 확인했다. 종료 후 검색은 281ms였다. 이는 각각 1회 측정이다.
- 저장된 공연 수는 5,615건으로 같았다. 기존 자료를 확인·갱신했으므로 처리한 작업 수만큼 공연 수가 증가하는 것은 아니다.
- 전체 6,011개 기존 레코드와 ID를 유지했고, 기존 좌표·완성 상세의 손실이나 하향 변경은 0건이었다. 메모·관심 저장 자료가 보존됐고 SQLite 무결성 검사도 통과했다.
- 전국 자동 갱신의 완료 상태와 마지막 성공 시각을 유지했다.

[운영 처리·검색 측정](verification/collection-performance-production.json) · [운영 자료 보존 검사](verification/collection-performance-integrity.json)

운영 화면에서는 지역 미선택과 전체 선택이 모두 전국 5,615건, 여수·원주 선택이 50건으로 검색과 지도 응답이 일치했다. 전국 지도에는 좌표가 확인된 5,601건을 표시하고 기존 좌표 대기 14건은 별도로 안내했다. 진행 상태 갱신 후에도 기존 지도 마커를 유지했다. 1440px 데스크톱과 390px 모바일의 카드·지도·지역 선택 화면에 가로 넘침이 없었고 JavaScript·콘솔 오류는 0건이었다. 화면 검수 중 수집 POST는 중립 응답으로 대체했으며 실제 쓰기 요청은 보내지 않았다.

원주 백운아트홀의 실제 건물 외곽과 층수 추정 높이 6m 모형이 표시되고 닫기 동작도 정상임을 확인했다. 다만 이 검수에서는 외부 배경 지도 타일이 12초 안에 로드되지 않아 시간 초과 안내가 표시됐다. 건물 모형은 계속 표시됐으며, 배경 지도까지 정상 로드됐다고 판정하지 않았다.
